How I build with Claude and sensitive data

A short and practical take on the sandbox + synthetic data setup I use when client IP can't leave their environment.

June 26, 2026

I’m currently building tools for clients using Claude Code. Those tools are designed to handle highly sensitive/IP data, yet Claude hasn’t seen any of it, thanks to the use of synthetic data or schema descriptions. The real data only meets the code in production, on the client’s infrastructure, where no AI lives.

The setup

Successfully sandboxing a coding agent takes a small amount of setup, almost no ongoing effort, and most of the cleverness is in choosing what the agent actually needs to see in order to be useful. My setup takes four steps, none of them complicated on their own.

1. The split

Claude Code lives on my machine. Real data lives on the client’s infrastructure. The two are kept geographically separated like exes at a wedding. They never have to be on the same machine because Claude is writing the code, then the code runs against the data on the client’s side.

2. Synthetic data

When I need to test, I generate values that look like the real values. For the regulatory tools I built last year for a medical manufacturer, one of them took bills of materials (BOMs) as input. To test without touching real BOMs, I generated fake ones, sometimes with a script, sometimes by hand. This means I sat at my keyboard typing fake part numbers like a 1996 data-entry clerk (ah, the AI times!). The skill here is in the messy edges: part numbers with internal conventions, the same supplier listed three different ways across rows.

3. Schema-only conversations

When Claude needs to know the shape of a database without seeing what’s in it, I share the schema and not the rows. Column names, types, and a short description of what each field means (e.g., “patient_id, varchar, unique per encounter, never reused”). That’s usually enough to get useful design help. There’s also a side effect: walking the schema with Claude tends to surface inconsistencies in the client’s data that nobody had named before (which can quietly add weeks of scope before I’ve written a line of code -- yay job security!).

4. Letting go of Claude

Claude writes the code. The code then runs without Claude in the path. The regulatory tool mentioned above runs on demand against the live BOMs and the client’s product catalog, and there is no LLM in the production path. The tool was built by Claude, and the tool runs on its own. The compliance team uses the output. Claude has never seen the product catalog.

The one place you can skip all of this

If your team is on Claude Enterprise (or another tool with a real BAA, zero-retention guarantee, and audit-ready logging), the contract does what the sandbox does manually. Data doesn’t go into training. The vendor can’t see it for “service improvement.” Logs are scoped and deletable. You can paste the real thing and move on.

The trade-off is cost. Enterprise tiers are a real budget line. The payoff is that you don’t engineer around the privacy concern on every project.

Final note

This whole space is moving fast and what works today will need revisiting in six months. The discipline is to keep the question open: what’s the safest thing I can do that still lets me ship? My answer right now is the four-piece setup above plus the Claude Enterprise exit hatch when the contract is in place.
